    경비가 왜 순공사원가 칸에 들어가 있을까?

    자세히 보기

    공고 23건의 원문을 DB 값과 일일이 대조하던 중, SRM에서 수집한 값이 순공사원가가 아닌 '경비'임을 발견했습니다. 컬럼을 분리해 스키마를 바로잡고, 기존에 잘못 적재된 데이터를 정정하는 스크립트를 만들었습니다.

    • 원인 검증: 공사 공고문 15건의 원문과 대조해 overHeadCostAmount 값이 '경비' 항목과 일치함을 확인
    • 스키마 개선: overhead_cost_amount 컬럼을 신설하고, 확인 전까지 순공사원가 컬럼은 결측(NULL) 처리
    • 데이터 정정: 기존 DB 957건 중 오류 데이터 1건을 특정하고, 백업 후 일괄 정정하는 스크립트 작성
    • 검증 일지 ↗
  • Bidmate_AI

    수집이 중간에 끊기면 처음부터 다시 해야 할까?

    자세히 보기

    SRM에 요청이 이어지면 공고 16건 내외에서 차단되는 현상이 발생했습니다. 수집 단위를 1건씩 즉시 커밋하도록 변경하고, 중단 지점부터 재개하는 체크포인트 로직을 구현했습니다.

    • 단위 저장 및 재개: 공고 1건 상세 수집 완료 시마다 DB에 즉시 커밋하며, 재실행 시 미완료 공고만 선별 수집
    • 차단 대응: 요청 차단 감지 시 10분 대기 후 자동 재시도하도록 예외 처리
    • 자동화 및 로깅: 매일 12시 Windows 작업 스케줄러로 자동 실행하고, 실행 이력을 collect_run 테이블에 기록
    • 수집기 문서 ↗
  • Bidmate_AI

    정정된 공고는 어떻게 알아챌까?

    자세히 보기

    공식 API에 '수정 시각' 필터가 없어 원본 데이터를 별도 저장한 뒤 신규 수집본과 비교하는 방식으로 변경 이력을 추적했습니다. API만으로 감지할 수 없는 경우는 별도 옵션과 문서화로 보완했습니다.

    • 변경 감지 로직: 저장된 api_raw 원본과 대조해 신규·정정(첨부 변경)·기본정보 갱신으로 분류하고 정정 공고만 재수집
    • 예외 보완: SRM 상세만 바뀐 공고를 찾는 --srm-revision-check 옵션을 추가하고, 공고일 변경 없이 내용만 수정된 경우는 감지 한계로 문서화
    • DB 스키마 문서 ↗
  • TVING Clone × AIOps

    모니터링 요청까지 공격이라고?

    자세히 보기

    트래픽 급증 시 악성 공격과 화제성 유입을 AI가 판별하도록 설계했으나, 내부 모니터링 API 호출까지 공격으로 오탐하는 문제가 발생했습니다. 판별 대상 경로를 실제 공격이 들어오는 엔드포인트로 제한해 오탐을 해결했습니다.

    • 도구 및 프롬프트 설계: Lambda 도구 8종과 Bedrock AgentCore 시스템 프롬프트 구현
    • 판별 규칙 고정: AI가 상황에 따라 보안 검사를 생략하지 않도록 '보안 판별 최우선' 규칙 명시
    • 스키마 정합성 확보: 반복되던 Unknown tool 오류를 해결하기 위해 Gateway Tool Schema와 Lambda 함수를 1:1로 매핑
    • AWS-tving-clone 저장소 ↗

Main Prompt

  1. 01원문과 대조하기

    Check every value against the original document before I use it. Mark anything you can't confirm instead of guessing.

  2. 02추측 전에 묻기

    If a requirement is unclear, state your assumptions or ask first. If there are several interpretations, don't silently pick one.

  3. 03요청한 것만 만들기

    Implement only what I asked, as simply as possible. No extra features, abstractions, or unnecessary error handling.

  4. 04관련된 줄만 고치기

    When editing existing code, change only the lines related to the request and follow the existing style. Mention unrelated issues instead of fixing them.

  5. 05단계마다 검증하기

    For multi-step work, show a short plan as "step → how to verify" first. For bug fixes, start with a test that reproduces the bug.

These are the rules I give AI coding tools when I work with them.
